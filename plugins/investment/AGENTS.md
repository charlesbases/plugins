# Investment 项目开发、验证与审查约束

本文件适用于 `plugins/investment/` 下的需求分析、设计、开发、验证、单测、文档与审查任务。项目级约束集中维护于此；各子链文档定义具体业务契约，不另立相互冲突的开发流程。用户明确的新指令优先，确认后的变更须同步相关项目文档。

## 1. 工作前先阅读项目约束

| 工作 | 阅读要求 |
|---|---|
| 所有任务 | 先读本文件，明确本次是文档整理、实现还是审查，以及授权范围 |
| 子链开发或审查 | 再读 [README](README.md) 的目标、当前状态和导航，以及 [架构](docs/architecture.md)、[公共契约](docs/contracts.md) 中相关责任和交接规则 |
| 输入输出、持久化或运行边界变更 | 阅读 [强格式入口](docs/spec/v1/README.md) 及相关 Schema、确定性规则和存储规范 |
| 特定子链任务 | 在项目约束之后阅读相应子链外部契约和必要内部流程；不能把子链文档当作全部项目约束 |
| 现有行为、根因或修改效果判断 | 阅读相关实现，追踪当前结论所需的入口、分发、核心分支、状态变化直至持久化或外部边界 |

项目约束审查只评价约束文档的完整性、一致性和可执行性，不自动扩大为各子链实现或模型效果审查。文档已更新不能证明代码已符合新规范。既往项目文档审查范围和结果见 [审查记录](docs/reviews/20261019-project-constraints.md)。

## 2. 实际使用场景与职责边界

1. 正式总链任务完整、顺序执行总链路。当前开发以单子链为单位：使用已定义并保存的上一子链输出示例，按当前子链输入契约绑定，不要求每次重新执行已完成的上游。正式总链运行仍按本轮上游验收结果交接；某链失败耗尽预算时停止后续执行。
2. 当前子链的验证脚本负责自身输出，不重复执行上一子链的业务验证，不重新解释、筛选或修改上游已确认事实。可以读取本轮实际输入及原始依据，以核对自身输出。
3. 第一子链没有上游，由入口负责登记用户提供的事实、确认来源及完成必要结构和运行边界检查；不能声称已经读取或核实无法访问的实际账户。
4. 必要历史业务记录及已完成上游的开发示例可以作为当前子链的合法输入。上游示例的来源和原验收状态须如实保留，不冒称本轮重新执行过上游；当前子链仍须实际执行流程及验证，不能拿当前子链的旧输出、缓存结果或既往验证结论代替本轮执行。
5. 每个子链明确问题、输入、输出、上下游用途及不承担的职责。内部适配器、分析器及步骤服务于准确产生外部输出，其私有约定不得改变对外字段、含义、单位、范围或错误语义。
6. 可以参考 `investment.bak` 的理论和业务链路，不参考其实现、函数划分或运行结果来证明新实现正确。

## 3. 三类脚本与主流程

| 角色 | 输入及职责 | 输出及权限 |
|---|---|---|
| 流程脚本 | 处理本轮子链输入及必要业务上下文，按已定义模型生成结果 | 候选业务输出或明确失败；不自签验证通过，不自行放行后链 |
| 验证脚本 | 独立核对当前输出的合理性、有效性及事实依据 | 强格式验证结果、失败定位、缺失事实及用途限制；不修改输入、证据或候选来使其通过 |
| 单测脚本 | 依赖上一子链已保存的输出示例，按当前输入模板，一次调用实际执行流程脚本和验证脚本，根据最终输出判断成功或失败 | 中断/未完成如实登记，不作为等待代理补做中间步骤的执行模式；不另做业务验收、不重跑上游、不拿旧结果冒充本轮成功 |
| 主流程 | 一次调用自动完成顺序调用、必要持久化和交接，不设重试 | 只执行一次流程及验证，失败立即返回并停止后链；通过才封存交接 |

验证独立性来自责任和推导依据，不来自文件名。流程与验证可共享 Schema、引用解析及精确数值等基础能力；验证脚本不能调用流程的业务算法来证明流程正确。

单测判断的是当前子链的流程执行结果：核对是否实际执行了流程和验证、运行状态与验证结果是否一致，以及必要产物和持久化状态是否成立。业务合理性、有效性、事实依据和业务数值复核由验证脚本负责，单测不重复实现。验证器校准是单独的开发步骤，其通过不能计为本轮流程执行成功。无上游的第一子链按既有入口事实登记要求准备输入。

业务输出、验证凭证、运行控制索引和单测报告分别表达。单测报告的 `invocations`、检查统计和进程日志不得混入业务载荷或充当下游业务输入。日期 manifest 的 `invocations` 是运行调用索引，不是交易流水。模拟数据来源与用途限制应如实保留，不能删除标记冒充真实用户事实。

## 4. 规则先行与强格式

实现前必须定义并写入相应契约及机器规则：

| 类别 | 必须明确的内容 |
|---|---|
| 对象与字段 | 字段名、类型、必填性、可空性、枚举、额外字段政策；未知、不适用、零和空集合分别定义 |
| 数值与时间 | 单位、币种、精度、取值范围、时间精度和时区、时间顺序、计算公式及容差依据 |
| 关系与状态 | 主键、引用、字段间约束、状态转换前提、去重及真实补充/更正的处理规则 |
| 科学模型 | 解决的问题、前提、适用范围、参数来源、计算方法、事实依据和不能支持的结论 |
| 输出资格 | 各项必要检查、有效用途、缺口影响、失败条件和结构化失败字段 |
| 持久化 | 必须跨轮保留的数据、数据库字段及约束、写入时点、增长方式和临时产物生命周期 |

JSON Schema/表 Schema 检查结构，确定性规则检查字段关系、业务约束与事实支持；两者均须落实。禁止只写“合法”“合理”等一句话，让 AI 自行解释执行标准。未知事实不得以零、空数组、估计值或默认常数冒充已确认事实。未完成强格式和必要验证规则的子链不能仅凭职责文档启用。

## 5. 事实依据、数据弃用与范围

1. 结论强度不得超过证据。事实、派生计算、明确模型下的推断及未知分别表达；未经支持的猜测不得作为事实或有效结论输出。
2. 验证脚本独立读取本轮实际输入及可核原始证据；不能只核对流程自行提供的“证明”。文件存在、引用正确并不等于内容支持结论。
3. 流程可以按已定义规则生成派生字段，不得擅自修改输入事实、补造缺失值、改写事实时点或替换依据。确需更新事实时，由用户或相应上游责任方提供新记录。
4. 数据无法取得或无法证实时，允许不采用该数据，但必须如实保留原对象或字段、实际获取/核验情况、弃用依据、缺口及影响。未取得不等于不存在，也不等于有据排除。
5. 弃用按事先定义、具有依据的统一规则执行。禁止针对个别基金、站点、测试名称或期望结果硬编码跳过、放行或补值分支。按来源选择不同解析适配器是正常内部实现，不能借此改变外部范围或输出标准。
6. 原始任务范围、候选全集及成功标准保持不变。不能将下载成功、模型就绪、有限预算或任意 top N 子集改称原始全集。剩余证据不足时，明确未知、待补证或目标未达成，不能缩小边界后宣布成功。
7. 一切以实际数据和已确认的实际使用场景为准。格式上允许、理论上可能或人工能够构造，不等于当前业务会发生；不得仅据此新增需求、修复项、兼容处理或验收阻塞。
8. 流程、验证、单测、主流程及辅助脚本均只实现当前实际数据、已确认调用方和现行契约所必需的处理。禁止为尚未发生的意外场景预先增加兼容分支、旧格式支持、兜底转换或自动补值；不得以预防未来问题为由扩展实现。
9. 意料外的场景真实发生后，先保留原始数据、实际入口、合法前置状态和失败证据，再追踪原因，做必要的最小修正或兼容，并补充对应的实际场景回归验证；不借机扩展其他假设场景。

## 6. 开发与运行顺序

开发顺序固定为：

```text
明确需求、职责及实际场景
→ 定义模型、输入输出、必要存储和强校验规则
→ 确定可达用例及独立预期，形成完整实施方案；仅未明确的业务取舍需用户确认
→ 先实现、校准并固定验证脚本
→ 再实现流程脚本
→ 单测复用已保存上游示例，实际调用当前子链流程及验证脚本，判断流程执行结果
→ 审查事实、流程、模型与验证依据，修复已确认问题
→ 重跑相关用例，分别交付业务输出、验证结果和单测报告
```

本轮运行顺序固定为：

```text
本轮合法输入及必要上下文
→ 流程脚本
→ 验证脚本检查当前输出的合理性、有效性及事实依据
  ├─ 通过：按契约提交、封存，交给下一子链
  └─ 失败：保存结构化原因，立即返回失败并停止后链；不重试
```

- 主链及所有子链均无自动重试：每次调用只执行一次流程脚本及一次独立验证（有完整候选时）。任何失败保存实际原因并立即结束本次调用，禁止后链；不把失败反馈给模型重新生成、不自动重跑、不以恢复名义再次执行。修复后另一次完整测试不能冒充前次运行通过。
- 重处理不能擅自改变本轮输入事实、方法、判断时点或验证标准，不能复用失败候选冒充重新执行。
- 流程未产生候选时返回明确的强格式失败，不伪造正常输出或验证通过凭证。
- 已提交但未收尾的操作须按已定义的提交状态处理，避免把已发生的业务重复记账；不能用恢复名义重置已用预算。
- 只有证明验证脚本存在漏洞或标准违背实际需求，才允许修改并重新校准。不能为了满足验证而偏离实际需求，或修改验证规则迎合流程输出。

### 6.1 单子链开发与输入输出示例

实际执行必须遵守下列约束：

1. 当前plugin由调用者一次调用，自动完成本次任务要求的完整流程并返回最终结果；单子链单测也必须一次调用完成“已保存的上游示例→流程脚本→验证脚本→执行结果”。允许流程脚本按source_id自动异步并发：Python负责采集时按来源插件化，Codex负责读取归纳时使用独立子session，由脚本自动创建、等待和汇总。禁止把子链拆成由外部代理逐批代做、登记或resume的步骤。
2. 执行开始后，禁止代理向生产者或验证者补发提示词、追加判断要求、修正解释口径、手工生成中间业务结果或替代流程脚本完成中间步骤。不设置失败后自动重生成反馈；方法、输入和验证标准不得中途改变。
3. 一次执行结束后，根据实际最终输出、独立验证结果和日志定位问题，修改流程脚本，再完整执行单测。禁止仅靠改提示、追加消息、手工修候选或另起调用反复生成来代替流程脚本修复。
4. 必要模型或外部能力无法由流程脚本自行完成时，返回明确失败；不得返回等待人工处理的HostRequest，再用多次resume拼成合规执行。分窗字段、工作计划、宿主协议或历史续行记录均不能豁免本条。
5. 文档更新不代表实现已达标。此前人工分步、提示干预或局部校准记录只能按实际状态保留，不能作为一次调用、无中途干预的验收通过证据。

- 每个子链维护一份输入示例和一份输出示例，按已经定义的字段、类型、引用和用途保存；已完成子链使用实际执行并验收后的记录，不再每次重做上游。
- 输入示例是本链 StageInput，输出示例是本链对外业务载荷。下一子链按输入角色读取上一子链输出，不把上一子链的 StageInput 整体当成本链输入；本链所需其他上下文按自身契约准备。
- 实际执行样例保存在 `~/.investment/test/<样例批次>/examples/<scXX>/input.json`、`output.json`，并用 `record.json` 登记原运行、原输入输出引用、候选/凭证/封存引用及允许用途。项目的[示例索引](docs/spec/v1/examples/README.md)登记位置和状态；保持被引用原文、数据表和运行记录可读。
- 单子链开发的上游输入只取示例索引登记的正式交接示例，不自行从历史运行中挑选专项试跑、成功子集或其他合法样例替代。登记缺失时先核实并补齐出处，不能以任一合法样例充当本次指定交接。
- 执行前核对示例原运行、输出引用及摘要、来源和文档范围与索引一致；当前输入必须绑定该完整输出并保留原有覆盖、失败、待补证和用途限制。数量按实际记录核对，不硬编码本次来源数或文档数。此核对属于输入交接职责，不扩大为单测中的业务验收。
- 单链单测以保存的上游输出及输入模板准备本轮输入，建立本轮调用身份，执行本链流程和验证；示例输出用于交接和说明，不是本轮预期结果缓存，更不代替本轮验证。
- 执行结论必须绑定本次输入、实际处理范围和本轮验证记录；局部试跑、验证器校准或旧输出通过不得报告为完整子链通过，等待、失败和未完成如实报告。文档规则、人工核对和程序已实现的拦截能力分别说明，不因写入规范就声称已有自动保障。
- 尚无已核实执行记录的子链保留其已定义接口及待登记状态，开发完成时补齐实际输入输出示例，不伪造成功输出或验收凭证。示例格式与实际执行记录须明确区分。

## 7. 单测准入与真实性

单测只验证已确认的实际使用场景，一切以实际数据为依据，不要求穷举，也不为覆盖率、边界组合或理论完整性扩展场景。每个单测场景在执行前须说明以下内容，缺少现实触发依据时不纳入：

| 项目 | 准入要求 |
|---|---|
| 实际入口 | 用户或本轮主流程确实可执行的操作 |
| 合法前置状态 | 使用已完成上游保存的合法输出示例及其引用材料；不要求本次重跑上游，首链遵守既有入口前置 |
| 触发条件 | 对应当前实际业务操作和实际数据，能够说明该数据如何进入并触发对应路径；不能只写理论上可能 |
| 本链输入 | 按既定输入模板绑定上一子链输出示例和必要上下文；保留来源标记，不手造上游输出或绕过流程装配当前候选，不为凑用例拼接事实、填充背景或组合边界 |
| 成功判据 | 根据一次完整执行的最终输出及本链交接规则判断成功或失败；中断/未完成如实登记，不人工接管中间步骤；不另定业务验收标准，局部校准不算本轮成功 |
| 判断依据 | 本轮实际流程和验证调用、运行结果、验证结果、必要产物与持久化记录；不独立重做业务数值或事实判断 |

禁止为了覆盖率构造实际使用中不可达的场景。正常成功、缺失、重复执行或失败场景均按上述条件准入；不能因其名为异常、验证器校准、反例或故障注入而豁免可达性要求。验证器校准也应遵守同一标准，不能伪造上游已验证的非法状态或编造业务来凑失败用例。

构造输入对某个函数的行为复现，与实际业务场景的触发证据必须分别记录。仅有构造用例失败而没有实际数据和合法调用路径依据时，只能记为待确认观察，不得列为当前验收阻塞，也不得据此要求新增修复或兼容。无需继续穷举来证明该观察。

修改前先明确哪个实际问题以及哪条规则被验证；不凭单测文件名或覆盖率指标新增业务需求。基础函数检查、静态文档检查和子链实际执行结果分别报告，不能相互冒充。

## 8. 审查方式与边界

按以下顺序审查，先建立业务与证据依据，再评价脚本是否通过：

| 审查层次 | 方法 | 必须有的依据 |
|---|---|---|
| 需求及范围 | 对照原始问题、职责、对象范围和成功条件，逐项映射到输出与规则 | 明确需求及已确认的边界，不能事后换目标 |
| 实际可达性 | 从合法初始状态沿实际入口推演操作、关键分支和状态变化 | 当前使用场景、输入契约或相关源码调用链；不能凭假设增设分支 |
| 流程合理性 | 逐步核对输入是否支持输出、步骤是否必要、未知及真实失败如何处置 | 本轮输入、流程和状态变化的因果关系 |
| 模型科学性 | 检查模型前提、适用范围、公式、单位、时间口径、参数依据和局限 | 模型原始依据及其对当前任务的适用论证；模型名称或引用不能代替论证 |
| 事实依据 | 将重要输出逐项对应到来源、原文/数据时点和实际计算 | 来源内容直接支持该字段或结论；不接受推测性证明或自证 |
| 验证独立性 | 验证脚本从需求、输入及模型独立复核关键结果，再比对当前候选；单测根据流程与验证的实际结果判断执行状态 | 验证规则独立于流程，不能共享同一个业务错误；单测不重复实现业务验收 |
| 真实执行 | 核对流程、验证、必要读写及结果，确认实际发生 | 对应真实可达用例的实际执行证据；通过率不替代需求满足 |

正式提出问题时须同时说明：需求依据、实际触发场景及合法前置状态、具体问题、直接证据、影响和修正边界。证据不足时明确无法确认，不当作已证实缺陷、不据此增加功能或扩大单测范围。完成当前任务所需证据充分后停止扩展审查。

审查禁止：猜测性输出；为过验证改变事实或需求；擅自缩小对象范围或成功条件；用硬编码分支绕开缺证据对象；将不可达场景提升为必须实现的功能；以校验通过、覆盖率或文档完整代替科学依据。

每次分别回答：执行是否成功、输出是否有效、原始需求是否满足。三者不能相互替代。文档审查仅给出文档结论；未检查实现或未执行测试时必须明确，不能宣称子链通过。

## 9. 正式数据与单测数据隔离

```text
~/.investment/
├── data/                                      必要正式业务数据
├── runs/<子链>/<YYYYMMDD>/<invocation_id>/     本轮正式输入、产物及验证材料
└── test/<test_run_id>/                        全部单测输入、数据库、产物、报告和辅助文件
```

正式根为 `~/.investment`，全部单测数据根为 `~/.investment/test/<test_run_id>/`。令 `P=resolve(~/.investment)`、`T=P/test`、`R=resolve(--root)`。正式根必须 `R=P`；测试根必须是 `T` 的严格后代，不能直接使用 `T`。模式、根及输入命名空间在读取输入、创建目录/锁或打开数据库之前强校验；测试输入及验证候选只能来自本批根，正式入口不得读取测试目录中的输入。`--root` 不得绕过隔离，测试数据禁止污染正式主流程，禁止使用 AppData 或系统默认临时目录。

SC01 的模拟来源为 `synthetic_fixture`，只能写本批测试数据库且保留 `observation_only`；正式用户事实为 `user_confirmation`。其他子链的来源字段按各自已定义契约表达，不能把模拟来源冒充正式来源。

`data` 只保留确有跨轮用途的必要业务数据；中间材料在 `runs`，不因其被使用过而永久入库。日期目录的 `README.md` 与调用目录同级，按实际记录说明每个 `invocation_id` 的内容、文件、状态及保留条件；清理不得删必要业务事实或破坏仍有效的用途。完整存储约束见 [架构中的运行目录](docs/architecture.md#runtime-data) 与 [SC01 存储规范](docs/spec/v1/sc01.md#必要数据存储)。

## 10. 协作与交付

- 用户只负责尚未明确的业务取舍；业务要求已经明确并已要求实现或修复时，技术方案、必要修改文件、共享组件修复和验证由代理自主推进，不因技术文件范围变化反复请求确认。确需用户决定时，说明具体业务取舍及其影响，不把技术实现选择转交用户。
- 遵守适用的 Cortex 工作流，用户明确指令优先于技能中的通用确认规则。仅要求整理文档时仍不擅自修改实现；已要求实现或修复时，保留必要分析、方案和证据，不把这些技术步骤变成额外的用户审批。
- 所有终端命令显式使用 Bash；禁止 PowerShell、pwsh、cmd 和 `.ps1`，读取文件与辅助命令同样适用。
- 结论有事实或源码依据，区分已确认、尚缺证据及未执行的验证；不以搜索片段、旧测试结果或文档声明推断当前实现正确。
- 生成或修改文件后，回答仅提供文件链接；未经用户明确要求，不自动打开文件、预览面板或外部应用。
