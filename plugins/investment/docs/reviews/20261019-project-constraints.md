## 2. 已修订的具体问题

| 原表述或缺口 | 修订 | 依据及边界 |
|---|---|---|
| 开发与审查约束散落，缺少统一阅读入口 | 新增 AGENTS.md；README、架构及公共契约链接项目入口 | 用户要求总结完整约束并审查项目级文档 |
| 架构标准交接把输入业务校验放在流程执行之前，当前输出验证责任不够清楚 | 明确上游验证自身输出、下游直接消费本轮结果；入口只承担必要结构与运行边界检查 | 不重复验证上一子链；当前验证器仍可回看本轮输入以核对自身输出 |
| 公共契约要求未产生候选时使用 InputCheck 与 Failure | 改为强格式 Failure，明确不以前置 InputCheck 替代输出验证 | 统一“流程脚本→验证脚本”；没有候选不能伪造通过凭证 |
| 架构仍规定复用缓存、重新验证有效期、只重跑受影响下游及局部重做报告 | 改为本轮完整顺序执行，失败在本链按三次预算重处理，真实事实更新形成新任务 | 不把已被用户排除的旧输出复用场景重新带回；必要历史业务记录仍可用 |
| README 将错误候选及故障注入泛列为补充控制测试，未明确可达性准入 | 单测与验证器校准统一要求现实入口、合法状态、实际触发及独立预期 | 真实性大于覆盖率；不能用测试名称豁免实际可达性 |
| 科学性和事实支持的审查方式缺少集中定义 | AGENTS.md 明确逐层方法、证据、问题提出条件及停止边界 | 不能只看格式、脚本退出或通过率；模型需前提及适用依据 |
| 数据弃用与缩小任务范围的界限不够集中 | 明确可以弃用无法证实的数据，但保留原范围、尝试、依据、缺口及影响，禁止硬编码跳过 | 数据缺失不能变成成功子集或降低目标的理由 |
| 单测报告可能被当成流程业务输出交付 | 项目约束集中区分业务输出、验证凭证、控制索引及单测报告 | invocations 等单测统计不得进入业务载荷；保留真实模拟来源标记 |
| 架构和公共契约的文档状态混有“待实现”“本轮仅建立文档”等时态 | 统一说明其为规范，实际实现进度另见总览 | 文档修订不表示代码已实现或当前验证已通过 |
