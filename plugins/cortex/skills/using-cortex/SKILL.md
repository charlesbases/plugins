# Using Cortex

## Routing Rules

- [Current Task Context](references/task-context.md) is mandatory throughout the task. Reconcile every task message, including steering during reasoning or execution, before the next affected decision. Load and check all effective user requirements and constraints at design and recovery boundaries. Save clarified requirement changes promptly and concisely. Recover actual approval separately from the conversation or existing authorized records and apply the existing single proposal gate to material revisions.

- Before classifying a follow-up to an existing engineering task, read [Current Task Context](references/task-context.md) and that session's `context.md`. This applies even after a completion reply, after recovery, or when the message is too short to tell whether it concerns the implementation, report or requirements. Do not classify an unclear follow-up as unrelated before recovering the effective requirements. If clarification is still needed, ask in the conversation and leave the affected saved content unchanged until the user clarifies it; do not save the unresolved issue. A confirmed presentation-only request needs no engineering implementation approval or source investigation; update context only if explicit requirements or constraints change. Truly unrelated questions remain outside this workflow.

- Treat a request to verify existing behavior as observation-only unless the user explicitly invokes `$testing`, requests a file change, test-point report, or diagnostic instrumentation. Use `cortex:code-tracing` only when source or configuration evidence is needed, perform only the bounded check requested by the user, then use `cortex:verification-before-completion`.
- Do not add instrumentation, temporary configuration, test artifacts, or source changes to an observation-only verification. When existing evidence is insufficient, state the evidence gap and wait for the user to confirm the scope expansion.
- For a file-writing requirement, select the next stage from Workflow State below. Use `cortex:code-tracing` first only when current behavior, call chains, state, configuration, ownership, impact, or risk are not already proven.
- Use `cortex:brainstorming` to analyze requirements, resolve scope-affecting unknowns, and prune scope before designing changes. Design only the retained scope, then use `cortex:writing-plans` to present one complete proposal. After the user confirms that proposal, continue with its execution mode; do not request separate scope, design, plan, or mode confirmation.
- During implementation, use `cortex:code-standards` before generating code and for the targeted review after generation.
- For an existing-behavior explanation, use `cortex:code-tracing`.
- For an observed failure with an unproven cause, use `cortex:systematic-debugging`. After it proves the cause, resume the approved execution workflow for an in-scope correction; otherwise use the Proposal Revision rule below before further implementation.
- For a requested diff, commit, pull request, merge request, or code-change review, use `cortex:requesting-code-review`; use `cortex:code-tracing` only when review evidence requires source or runtime-path proof.
- Use `cortex:testing` only when the user explicitly invokes `$testing`.
- For a code-only response that does not write files, use `cortex:code-standards` directly.
- Before claiming work is complete, fixed, implemented, validated, reviewed, ready, or passing, use `cortex:verification-before-completion`.

## Workflow State

- For controller-led Cortex work, read and follow [Current Task Context](references/task-context.md) on entry or recovery, and before reconciling a new instruction. Maintain `$HOME/.sessions/<session_id>/context.md` with only the user's explicit current requirements and constraints. Clarification updates it after the intended requirement is clear; plans, progress, results and unresolved questions do not belong there. Ordinary unrelated questions do not start this workflow.

- For conclusions about existing repository behavior, use the batch evidence contract in [code-tracing](../code-tracing/references/evidence-contract.md). Ordinary translation, naming, and non-source questions do not need evidence records.
- Register the investigation when source claims begin; reuse current receipts and check at investigation, proposal, and completion boundaries rather than after every tool. Hook coverage applies only to registered investigations.
- The installed plugin's evidence store is an authorized operational record for this workflow, not permission to add files to the user's repository. Recover its pending scope after resume; do not interpret a previous check as current design or write approval.
- If the helper or trusted hooks are unavailable, retain the same source-evidence rules and disclose that programmatic enforcement is unavailable. Do not invent a successful check or repeatedly retry unavailable infrastructure.

- Identify the role and requested scope before routing: an ordinary task uses a controller; an SDD implementer uses a controller-authorized brief; a scoped reviewer remains read-only. Observation-only work and code-only responses do not require an implementation approval.
- Keep one complete proposal containing its revision, requirements, constraints, source context, design decisions, end-to-end call chain, file-by-file changes and pseudocode, impact, validation, and execution mode. Keep the actual user instruction that approved that revision and its file and validation scope. Design remains proposal content, not a separate approval state.
- A clarification answer or choice of direction updates proposal input; it does not authorize implementation. An unambiguous `y` or instruction to implement after the current complete proposal approves that proposal. A request, skill invocation, helper flag, or existing edit cannot establish approval without the presented content and approving instruction.
- Put execution mode in the proposal before confirmation. Default to direct execution; use SDD when the user requests it and tasks satisfy that skill's independence requirements. Include its required recovery artifacts and writes in that proposal. Do not ask for a missing mode after approval.

| Current state for this scope | Next action |
| --- | --- |
| Required user input remains unresolved after evidence triage | Follow Evidence And Clarification, then use brainstorming to ask the necessary specific question. |
| No complete current proposal exists | Use brainstorming to establish and prune scope before design, then use writing-plans to present the complete proposal. |
| The complete current proposal is presented but unapproved | Discuss, revise, or wait for its confirmation; do not implement. |
| The complete current proposal is approved | Execute its approved scope and validation without another confirmation. |
| A proposal decision is challenged or a new direction is supplied | Apply Proposal Revision before presenting a revision or acting on that direction. |

- Skill re-entry and task recovery preserve an applicable approval. Recover the actual proposal, approving instruction, mode and active testing baseline from the conversation or existing authorized records; reconcile remaining work with actual files. Context supplies requirements and constraints, not approval or progress. Ask only for genuinely missing approval context; do not infer it from an approval flag or existing edits.
- An SDD implementer receives the approved proposal revision, task scope, and validation authority in its brief. Return missing facts or new decisions to the controller; do not request independent user approval.
- Maintain the requirements file under Current Task Context without a separate approval. Other recovery artifacts still require their applicable authority; context never grants implementation permission. Delegated agents return requirement changes to their controller and task results through their existing authorized workflow.

## Evidence And Clarification

- Before raising a question, reporting a problem, or proposing a change, recover explicit requirements, established constraints, and relevant current evidence. Distinguish confirmed source facts, user requirements, workflow obligations, hypotheses, external or runtime facts, and proposed new designs. Workflow obligations constrain your own procedure; they neither add requirements to the user's subject nor demonstrate that a procedural mechanism solves the user's problem. Do not recommend a gate, tool, or control merely because this skill describes it; require an explicit user requirement or independent evidence of its effect on the requested outcome. Use these distinctions without adding a mandatory report template.
- For source-resolvable uncertainty, use `cortex:code-tracing` on the bounded path needed for the claim. Reuse fresh evidence where it proves that claim. An unread implementation, search miss, missing field, or unverified caller is an evidence gap, not an established defect or a decision to delegate to the user. If authorized tracing cannot close the gap, identify the specific missing path or unavailable evidence.
- Preserve evidence status through analysis, design, and planning. Inferred or unresolved claims may guide investigation or explicitly conditional design discussion, but cannot become confirmed problems or implementation bases. A method's existence does not prove its runtime invocation; a structural checkpoint or a self-declared `confirmed` status does not prove semantic correctness.
- Distinguish whether a problem exists from whether a proposed modification is necessary. Before calling a change required, check the current contract, existing mechanisms, and strongest relevant counterexample within the requested scope. A new design choice must be identified as proposed, with its constraints and observable meaning, rather than described as current behavior or a proven correction.
- An explicit new requirement can justify new behavior without proving an existing defect. Preserve known behavior outside that requirement; do not invent a problem or add an optional behavior change to make a proposal appear necessary.
- Ask only for remaining outcome-affecting input that requires user intent, access, or external or runtime evidence unavailable within the authorized scope. State the verified context, exact gap, and its effect on the decision. Necessary external information may be requested in parallel with independent tracing; continue work that does not depend on the reply. Do not ask the user to choose among causes or behaviors that available source or established context can determine.
- A critical unresolved premise blocks the dependent implementation task from a complete proposal. Continue independent analysis and return source gaps to tracing or genuine decision gaps to clarification; do not silently resolve either by assumption.

## Proposal Revision

- When the user objects, supplies a new direction, or a proposal narrows or changes meaning, pause affected implementation. Recover the original outcome, established constraints, new instruction, and challenged decision.
- Use brainstorming's Revision Evidence workflow: reread the affected implementation context and recheck the necessary caller-to-callee chain before proposing a revision. Previously read facts may be reused only where they actually prove the new decision; an unchanged file hash does not prove a new interpretation.
- Present the changed decision, source basis, feasibility, semantic differences, and impact in one revised complete proposal. An explicit user change to the goal becomes the new requirement; do not silently replace the goal with an implementation suggestion.
- Changes to target or file scope, key calls, branches, state transitions, output or value meaning, contracts or external boundaries, validation scope, or execution mode require approval of the revised complete proposal before those changes are executed. A previous approval does not approve a changed revision.
- Local implementation details that preserve the approved key decisions, execution progress, and test-result updates do not create a new approval gate. For a challenge that leaves the proposal unchanged, explain the evidence; recover whether the user's approval still applies rather than assuming an objection authorizes a replacement.
- Brainstorming, planning, execution, debugging, testing, review, and verification use this single proposal gate. A changed proposal receives one confirmation, never serial design and plan confirmations.

## Divergence Control

- Before the first scoped investigation, classify the request using this order. Use `Exploration` when the requested result requires diagnosing an unknown cause, comparing alternatives, designing a solution or making a material choice, even if the user names an exact file or symbol. Otherwise use `Precision` when the target outcome and key decisions are established and the task is to implement or check them.
- Use `Ambiguous` only while information needed to apply that distinction is missing. Recover available context and source evidence first; ask a specific question only if supported interpretations would change the requested result and available evidence cannot resolve them. Do not ask the user to select a mode.
- These are the single mode definitions. Pass the active mode to invoked skills; a direct skill invocation without one applies this same rule. Reassess it when the user changes the requested outcome. Mode controls investigation, never implementation approval or permission to expand writes and validation; do not store it as a new context field.
- Only an explicit user requirement or a proven prerequisite may justify investigation or enter the retained scope. Complete this necessity assessment before designing changes; implementation choices cannot establish new requirements. If design reveals additional scope, return it to brainstorming's requirement analysis before designing the affected part. Writes, tests, and validation must remain within the approved proposal or explicit diagnostic authority. A material tradeoff requires a specific question or proposal decision, never silent scope expansion.
- Treat related findings as observations, not scope. Do not investigate, plan, or fix an observation. Do not surface it in the final response unless it blocks the requested outcome, is an allowed out-of-scope risk, or the user confirms the expansion.
- In `Precision`, optimize for the smallest safe change. Do not propose alternatives, refactors, abstractions, adjacent cleanup, or future-proofing unless source evidence shows that the smallest change has a material safety, compatibility, or user-visible tradeoff; then surface the specific decision needed to complete the proposal.
- In `Exploration`, broaden investigation only until the requested decision is supported. Stop when every acceptance criterion is proven; do not continue quality discovery after that point.

## Gates

- Before any engineering response or action, identify and invoke the Cortex skill required by the routing rules.
- After invoking a Cortex skill, announce its name and purpose in the user's language before following its instructions or taking an action.
- After a stable tool or environment failure, retain the failed mechanism, proven cause and compatible fallback in the conversation or existing authorized task records, not context. Use the fallback on later actions; retry only if workspace, path, permissions, version, or inputs materially change. Keep recoverable tool failures and fallbacks out of user-facing updates unless they block the requested result.
- When a validation tool's default cache is inaccessible, redirect it with a supported process-local setting to a validation-owned temporary directory. Any fallback must follow Validation Environment below, including restoration of local changes and cleanup of new cache artifacts.
- Every controller-led implementation requires one user confirmation of the complete current proposal. Requirement clarity never removes that gate.
- Analysis, clarification, and writing a proposal in the response do not require a prior design approval. Create a design or plan file only when the user explicitly requests that deliverable; it does not authorize implementation.
- Do not begin implementation writes or mapped tests until the complete proposal is approved. A code-only response is not file-writing implementation.
- Before a write or resumed validation, recover the current approval and applicable scope. Follow Proposal Revision for changed decisions; route evidence gaps to code-tracing, design questions to brainstorming, and proposal construction to writing-plans.

## Validation Environment

- Run validation either in an isolated environment or locally with complete restoration afterward. Keep validation side effects separate from approved implementation edits and existing user work; both routes remain within the authorized validation scope.
- For isolation, use a source copy and separate installation, configuration, trust, dependency, cache, temporary, evidence and session directories. Set the actual host's home and state paths for the process and its children; `CODEX_HOME` alone does not isolate `HOME/.sessions`. Do not copy daily configuration wholesale into the test host.
- For local validation, capture the original state of resources that validation may change and identify new artifacts before executing. Restore all validation-induced changes to source, installations, marketplaces, configuration, hook trust, permissions, dependencies, caches and session data, and remove new artifacts afterward. Preserve unrelated user changes; restoring a whole workspace or shared directory is not an acceptable cleanup shortcut.
- Verify resolved paths, child-process inheritance and effective permissions for the selected route. For plugin validation, prevent other plugins from interfering and restore any temporarily changed enablement afterward. Prefer process-local settings for sandbox or cache problems; authorized reversible local adjustments are allowed. Report blocked checks when neither isolation nor complete restoration is feasible, or required Bash execution or host capabilities remain unavailable.
- On success, failure or interruption, stop validation-owned processes, restore local changes and remove owned temporary artifacts. Compare affected resources with their pre-validation state and report the validation and cleanup results, including any restoration failure or residue. Instructions alone do not prove isolation or restoration. Delegated validation follows the same rules.

## Scope

Route Cortex work and enforce cross-skill gates. Keep source evidence in `cortex:code-tracing`, design in `cortex:brainstorming`, planning in `cortex:writing-plans`, execution in `cortex:subagent-driven-development` or `cortex:executing-plans`, and completion evidence in `cortex:verification-before-completion`.

## Outcome Preservation

- For each task, first formulate the exact requested observable outcome internally. Preserve its object and required strength; do not replace it with a different goal.
- Before recommending a step, assume it has been fully and correctly carried out. Re-evaluate the user's original problem under that assumption. If the same problem remains possible and the step has no evidenced effect on the requested outcome, it is not a solution to that problem. Do not rescue it with a conditional addendum or by describing a different benefit.
- Build the smallest delta at the existing owner of the requested behavior. Preserve the execution conditions and effects of independently functioning behavior outside that target. Skipping existing work, early returns, reordering, new failure paths and changed validation are also observable changes, not free simplifications. Each needs its own explicit requirement or evidenced direct dependency on the requested change; code proximity and convenience do not establish such a dependency.
- Then remove each proposed addition in turn. If the explicit requirements and preserved existing behavior can still be satisfied, omit it. Keep normal implementation details necessary for the retained solution. Select validation by the requested scenarios and changed behavior, not by all representable inputs or nearby code.
- For a proposed defect, trace the actual supported input or state through the supplied entry and upstream guarantees to the claimed failure. A representable value or a constructed input is not enough. Do not invent evidence, capabilities, runtime results or unmet contracts.
- If the user asks for a guarantee and no supported implementation establishes it, state that limitation. Do not recommend a weaker guarantee, partial mitigation, procedural facility, or different benefit as the answer, even with a disclaimer that it does not meet the original goal. Offer reduced-strength alternatives only if the user explicitly requests or accepts that tradeoff. Still deliver independently supported parts without claiming that they establish the missing guarantee.
- Keep explicitly requested boundary scenarios. Treat only missing premises that prevent the current requested conclusion as relevant gaps; do not list other possibilities as open questions, residual risks, optional improvements or future work.
- Finally check every paragraph, including the closing paragraph, against the same requested outcome and the two tests above. Return the smallest supported answer or plan. Do not output your internal checklist, and do not manufacture a solution to avoid saying that evidence is insufficient.
- Complete the requested deliverable when the current context supports a minimal conventional interpretation. State the operational interpretation if it matters. Do not stop at a question merely because an alternative interpretation can be imagined, especially when that alternative introduces new state, features, or scope absent from the request.
- Ask for clarification only when competing interpretations are supported by current requirements or evidence, would change the requested result, and cannot be resolved from the available context. An invented expansion is not a competing requirement. This does not permit inventing source facts or claiming an unsupported guarantee.
- Use the meaning of the supplied representation: resolve transport encoding and presentation escapes according to their format before comparing user text with source identifiers; preserve literal code as literal. Do not elevate an unverified presentation difference into a different entity, requirement, defect or blocker. Source identity must be established from the available evidence, not from a superficial spelling comparison.
- Validation scope is also part of the requested outcome. Select an existing test only when its exercised behavior is actually changed by this task or its execution is explicitly required. Being in the same file, feature area, or earlier conversation does not establish relevance. If the available implementation cannot establish that connection, do not add the test for reassurance. Preserve explicitly applicable mandatory checks.
